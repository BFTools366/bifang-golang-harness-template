# 下游项目初始化表单

收到创建新下游项目的请求后，先完成本表单，再执行 Harness 验证、环境安装、目录创建、复制、Git 初始化或其他写操作。用户已经在当前请求或后续回复中明确给出的合法字段直接记为已解析，不得重复询问。

## 交互规则

- 维护字段状态：`待首轮询问`、`待条件询问`、`待校验`、`已解析`、`不适用`。中文项目展示名称、英文项目展示名称、`project_id`、项目路径、负责人是全部基础字段；首次问询必须用一份清晰编号的表单，一次列出其中全部尚未解析字段，不得拆成逐字段多轮，也不得用“请提供初始化所需信息”这种无字段提示代替。接口、Agent 策略模式与交付平台已关闭，不属于基础字段，不得进入问询。
- 中英文项目展示名称至少由用户直接提供一个。只提供中文时，Agent 在本轮解析中自动翻译并补齐英文；只提供英文时自动翻译并补齐中文，不为译名增加单独问询。原名称含难以直译的专有名词、品牌词或造词时，补齐的另一语言名称允许采用音译、约定俗成译名或保留原文形式，不强求逐字语义翻译，只要在目标语言中可读、不产生歧义即可。两个名称都由用户提供时保持原值，不自行改译；两个都未提供时在首轮同时询问。自动翻译得到的名称必须标记来源，并与用户原始名称一起进入最终完整汇总；用户对汇总的确认同时构成对译名的确认，确认前仍不得写入。
- **已关闭字段**：接口组合、Agent 策略模式、`user_owned_tasks`、`superpowers`、`parallel_worktree_subagents`、`acceptance_smoke`（含 `e2e_hint`）在本阶段全部固定为下表取值，**不向用户展示、不询问、不提供选择**。用户主动提出修改时说明当前模板阶段不开放，不解析为表单字段。接口固定为 HTTP API；交付平台固定为 Linux；策略固定为下文「固定策略」一节所列取值。
- 首轮回复后先校验全部基础字段。若其中有缺失或非法值，只集中列出仍需修正的基础字段、各自约束和原值问题；已经合法的基础字段继续复用，不得重问。基础字段全部解析前不得进入条件问询。
- 基础字段全部解析后，仅按实际需要补全仍然开放的条件字段。当前开放的条件字段有两项：`user_api`（是否启用用户 API，默认 `enabled`）与 `graphql`（是否启用 GraphQL 只读查询层，默认 `disabled`，且仅在 `user_api=enabled` 时可选）。两者都在首轮一并询问，因此基础字段收齐后直接进入完整汇总。
- 用户主动一次提供多个字段时全部解析并记录来源；合法字段不得为了遵守顺序而重问。字段非法时只说明该字段的约束并重新询问同一项。
- 所有必填和条件字段收齐后，展示一份完整汇总，其中必须包含中英文项目展示名称及各自来源、用户输入的项目路径、解析后的最终项目根目录、派生的 kebab-case 前缀与 Go module 路径、`user_api` 取值、`graphql` 取值、接口和固定策略取值；并说明接口、`user_api` 与 `graphql` 将在中性工程事实文件 `.harness/go-service-profile.json` 中持久保存，供后续构建使用。汇总同时说明本工程只提供 Go 后端服务能力，项目形态固定为 Go 服务（接口固定 HTTP API），交付平台固定为 Linux；不存在 GUI、托盘、通知、自启、深链接或全局快捷键等桌面能力字段。本轮只询问是否按该汇总创建。
- 在用户确认完整汇总前，只允许读取规则、检查已有路径和运行只读解析；不得创建目录、复制文件、安装环境、初始化 Git 或修改任何文件。
- 当前 Harness 源只接收创建终端下游所必需的本表字段；不接收产品目的、核心输入/输出、业务规则、成功标准、风险、副作用、产品专属接口路径/文案/数据、远程地址、凭据、反馈渠道或发布需求。即使用户主动提供，也不得把这些内容解析为表单字段、写入 Harness 源、复制到中性脚手架或提前实现；只说明它们已超出当前模板阶段，并要求初始化完成、工作目录切换到 helper 返回的唯一 `targetRoot` 后，再通过 `$go-define-product` 重新提出。

## 首轮基础问题模板

首次问询只列出用户尚未明确提供的基础字段，并保持以下编号和约束可见。本模板**只有七项**（五项基础字段加两项条件字段）；接口、Agent 策略模式与交付平台已关闭，不出现在问询中：

1. 中文项目展示名称：面向中文用户显示；中英文至少提供一个，缺少另一个时自动翻译。
2. 英文项目展示名称：面向英文用户显示；中英文至少提供一个，缺少另一个时自动翻译。
3. `project_id`：ASCII `snake_case` 标识。
4. 项目路径：最终项目根目录或父目录。
5. 负责人：真实负责人或明确的责任主体。
6. 用户 API：是否启用账号与认证能力。**默认启用**；不需要时回答「否」，脚手架将不包含任何账号、认证或令牌相关代码。
7. GraphQL：是否启用 GraphQL 只读查询层。**默认关闭**；需要时回答「是」，脚手架将带上 `/graphql` 端点与 gqlgen 代码生成配置。它只提供 `health` 与 `me` 两个查询、不含任何写操作；因为 `me` 依赖账号与组织实体，本项仅在用户 API 启用时可选 —— 用户 API 回答「否」时本项固定为「否」，不再单独询问。

这七项之外，**不得**再向用户列出任何可选项。接口固定为 HTTP API、交付平台固定为 Linux、Agent 策略固定为「固定策略」一节的取值，三者均为「模板固定值」，不询问、不展示、不接受自定义。

## 固定策略

以下取值在本阶段硬编码，不随用户输入变化，也不在首轮问题模板中展示：

```yaml

user_owned_tasks: disabled
superpowers: disabled
parallel_worktree_subagents: disabled
acceptance_smoke: enabled

```

这些字段一律视为 `已解析`，来源为「模板固定值」，不得进入条件问询，不得因用户主动提及而改写。

用户已在创建请求中合法提供的基础字段不再显示；其余基础字段必须在这一轮全部显示。

## 字段阶段与顺序

| 顺序 | 阶段 | 字段 | 解析规则 |
|---|---|---|---|
| 1 | 首轮基础 | 中文项目展示名称 | 中英文至少一个由用户直接提供；只缺中文时由 Agent 从英文自动翻译，记录为自动翻译并等待最终汇总确认。 |
| 2 | 首轮基础 | 英文项目展示名称 | 中英文至少一个由用户直接提供；只缺英文时由 Agent 从中文自动翻译，记录为自动翻译并等待最终汇总确认。 |
| 3 | 首轮基础 | `project_id` | 必填；必须匹配 ASCII `snake_case`：`^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$`。该正则在语法层已排除大小写混用、横杠、点、空格、非 ASCII 字符、数字开头、连续下划线与结尾下划线，因此该标识可直接充当 Go module 路径。另需拒绝会与 Go 标准库或常见依赖混淆的名字：`internal`、`net`、`http`、`test`、`main`、`gorm`、`gin`、`log`、`json`、`common`、`utils`、`config`。可以提供建议值，但必须由用户确认。 |
| 3a | 派生（不问询） | Go module 路径 | 由 `project_id` 确定性派生，**不单独问询**：module 路径就是 `project_id` 本身，不带域名或组织前缀（`go.mod` 的 `module` 行与全部 `internal/...` 导入前缀均使用该值）。`project_id` 确认后自动得出，并在完整汇总中一并展示。裸 module 路径不影响 `go build`/`go vet`/`go test`/`go mod tidy`；它只表示当前 module 不可通过 `go get` 从远端获取，因此不得依赖任何以 module 路径为根的远端导入。**必须保持无点号**：一旦写成 `<project_id>.com` 之类，Go 会把它判定为域名并发起 `?go-get=1` 网络解析，导致 `go mod tidy`/`go get` 失败。 |
| 4 | 首轮基础 | 项目路径 | 必填；允许输入最终项目根目录或其父目录，允许绝对路径或相对 Harness 根目录的路径。按“目标路径解析”计算最终项目根目录。 |
| 5 | 首轮基础 | 负责人 | 必填；记录真实负责人或用户明确指定的责任主体。 |
| 6 | 首轮条件 | 用户 API | 条件字段之一；取值 `enabled` / `disabled`，**默认 `enabled`**。用户回答「否」时记为 `disabled`，不复制 `assets/go-service-user-api/` 的任何文件、不注入 `AllModels()`/`Modules()`、不引入 `github.com/golang-jwt/jwt/v5` 依赖；回答「是」或未明确表态时记为 `enabled`，按条件资产说明覆盖并注入。 |
| 6a | 首轮条件 | GraphQL | 条件字段之一；取值 `enabled` / `disabled`，**默认 `disabled`**。用户回答「是」时记为 `enabled`，按 `assets/go-service-graphql/` 的说明覆盖并注入 `Modules()`、`go.mod` 与 `configs/config.yaml` 的 `graphql.enabled`；回答「否」或未明确表态时记为 `disabled`，不复制任何文件、不做任何注入、不引入 gqlgen 依赖。**硬依赖**：`user_api=disabled` 时本项必须是 `disabled`，不得单独启用（`me` 查询依赖账号与组织实体）。 |
| 7 | 固定（不问询） | 交付平台 | 固定为 Linux 服务端；**不作为可选项展示**，也不接受其他平台。构建与发布默认产出 `linux/amd64` 与 `linux/arm64` 无 CGO 静态二进制。 |
| 8 | 固定（不问询） | 接口 | 固定为 HTTP API；不作为可选项展示，也不接受其他接口形态。 |
| 9 | 固定（不问询） | Agent 策略模式 | 固定为「推荐预设」，即下文「固定策略」一节的取值；不询问、不接受自定义。 |

## 默认交付形态与启动命令

交付平台固定为 Linux，因此初始化完成后不再询问平台，直接按以下默认形态交付并把启动命令写入完整汇总：

- 构建目标：`GOOS=linux GOARCH=amd64 CGO_ENABLED=0`（发布矩阵另含 `linux/arm64`；详见 `docs/RELEASE.md`）。
- 制品命名：`<product>-v<version>-linux-<arch>`（无扩展名）。
- 开发态启动（源码目录内）：`go run ./cmd/server -e dev`。
- 构建后启动（Linux 服务器）：
  ```sh
  chmod +x <product>-v<version>-linux-amd64
  ./<product>-v<version>-linux-amd64 -e prod
  ```
- 环境变量 `APP_ENV` 等价于 `-e` 参数；配置文件按 `configs/config-<env>.yaml` 加载，可用 `CONFIG_PATH` 覆盖。
- 健康检查：`GET /healthz` 返回 200 视为进程就绪（存活探针，不查依赖）；`GET /api/v1/system/health-check` 额外校验依赖可用性。Swagger UI 位于 `/swagger/index.html`。

其他平台的交叉编译不在默认交付范围内；用户后续明确要求时，按 `$go-build-release` 的矩阵扩展，而不是回填初始化字段。

## 初始化完成后的 Swagger 展示

初始化写入、Git 初始化与 Harness 验证全部成功后，按以下顺序自动展示接口文档，无需用户额外要求：

1. 在最终项目根目录执行 `go mod tidy`，随后以开发环境启动服务：`go run ./cmd/server -e dev`（后台运行，保留进程句柄）。
2. 轮询 `http://127.0.0.1:<app.port>/healthz` 直到返回 200，最长等待 30 秒；端口取 `configs/config-dev.yaml` 的 `app.port`。
3. 用系统默认浏览器打开 Swagger UI：`http://127.0.0.1:<app.port>/swagger/index.html`。
4. 在最终汇总中给出 Swagger UI 地址与 `healthz` 地址，并说明服务仍在后台运行；用户确认后按需停止进程。

启动失败时不得静默跳过：必须报告失败阶段（`go mod tidy`、编译、监听端口）与原始诊断，并保留手动启动命令供用户复现。Swagger 路由由 `internal/api/router.go` 注册，`docs/` 目录由 `swag init` 生成；脚手架已包含 Swagger 注解与路由，无需用户额外配置。

## 目标路径解析

收齐 `project_id` 与项目路径后，运行只读 helper：

```text
python3 .agents/skills/go-instantiate-project/scripts/resolve_project_target.py \
  --harness-root <harness-root> \
  --project-path <user-project-path> \
  --project-id <project-id>
```

解析规则固定如下：

1. 相对项目路径以当前 Harness 根目录为基准转为绝对路径，并规范化 `.`、`..` 与已存在的符号链接祖先。
2. 规范化输入路径的最后一个名称与 `project_id` **区分大小写地精确相等**时，最终项目根目录就是该输入路径。
3. 最后一个名称不精确相等时，最终项目根目录为 `<项目路径>/<project_id>`。不得用大小写、连字符/下划线转换、前后缀或相似度把不同名称视为相同；例如 `sample-tool` 与 `sample_tool` 不相等，结果为 `sample-tool/sample_tool`。
4. “不存在或为空”只约束最终项目根目录；作为父目录输入的项目路径可以已经存在并包含其他项目或文件。最终根目录若为符号链接、非目录或非空目录，必须停止且不得覆盖。
5. 最终项目根目录不得是 Harness 根目录或其任何祖先。通过已存在符号链接解析后再次执行同一检查；目标位于 Harness 内部时仍须在复制前冻结源文件清单并排除目标，以阻止递归复制。
6. helper 输出的 `targetRoot` 是后续复制、Git 初始化、开发、验证、构建和发布准备唯一使用的规范化项目根目录。完成表单汇总时同时显示原始输入与该值。
