# 治理 Harness 自身记忆历史

Harness 对自身的 ADR、Changelog 应用与下游相同的“按日记忆只保留最新文件”规则（见 ADR-20260805-004），但每份最新文件的写入规则要求综合携带此前仍然有效的条目，天然只增不减。本 Skill 是 Harness 自举自身治理能力的维护工具：把不再被任何当前规范引用、已被后续决定完全取代的旧条目原文迁移进同目录 `<TYPE>_history.md`，让当前文件只保留仍在直接约束行为的内容，同时永久保留完整原文供人类和 Agent 追溯，不依赖 `git log` 才能读到叙事。

## 适用范围与准入

- 只治理 Harness 根目录自身的 `docs/adr/` 与 `docs/changelog/`；不适用 `docs/work_plan/`、`docs/project_status/`、`docs/product_spec/`——这三类文件的写入规则要求每个自然日整篇重写为当前完整快照，不逐条累积历史决定，没有同类膨胀问题，历史继续完全交给 Git。
- 本 Skill 不得加入 `$go-instantiate-project` 的复制清单，也不得被任何下游初始化、升级或迁移流程引用或复制；`docs/adr/`、`docs/changelog/` 本身在实例化时已被排除复制，下游从零积累自己的记忆，没有需要迁移的历史条目。终端下游不得保留、发现或独立重建本 Skill；下游若产生同类需求，须由项目负责人另行确认后单独设计。
- 只在以下情形之一触发，不作为日常 ADR/Changelog 写入的自动步骤：当前最新文件行数超过本仓库人工维护文本 500 行建议重构阈值；或项目负责人明确要求整理/清理历史记忆。日常 ADR/Changelog 写入不因本 Skill 存在而改变其自身写入规则。
- 执行前必须完整读取目标目录当前最新文件、其 `README.md` 索引与写入规则，以及 `AGENTS.md`、`docs/ENGINEERING_RULES.md` 中对该目录的引用。

## 工作流程

1. 对目标目录（`docs/adr/` 或 `docs/changelog/`）的当前最新文件，逐条切分独立条目：ADR 按 `## ADR-YYYYMMDD-NNN` 标题切分，Changelog 按其内部可独立归档的最小结构单元切分。
2. 对每个条目做取代粒度判定，不得只看条目是否“较旧”：
   - 标题或正文没有任何“已由 ADR-YYYYMMDD-NNN 取代”“取代范围”等标记，且在全仓（排除该文件自身与目标 `_history.md`）检索其稳定标识未发现被更晚条目列为取代对象：视为仍然完整有效，不迁移。
   - 标题标记“已由 ADR-YYYYMMDD-NNN 取代”但同时注明某分支/某方面“继续有效”，或更晚条目的“取代范围”只点名了该条目的部分字段：该条目仍不得整条迁移；只有当逐字段核对后确认没有任何一句仍是当前行为的直接依据、也没有被别处引用时，才可迁移整条。多数“部分取代”条目应保守判定为不迁移。
   - 条目已被更晚条目的“取代范围”完整点名取代、正文不含任何后续被引用或独立仍生效的字段、且全仓检索确认其稳定标识只出现在被取代声明中：判定为过期，可迁移。
   - 上述判定无法确定（既无引用也无明确的完整取代声明）：保守保留在当前文件，不得仅因日期较早迁移；在完成报告中列为“候选”交人工复核，不自动迁移。
3. 对判定为过期的条目，把原文一字不改追加到同目录 `<TYPE>_history.md` 末尾（文件不存在则新建，标题为 `# <TYPE> 历史决定`，并在文件顶部说明：本文件只追加、不重写、不删除，是从当前最新文件迁出的完整过期条目原文，需配合 Git 历史使用，不是下游可继承的项目记忆）；随后从当前最新文件中删除该条目。写入 `_history.md` 的内容永久不得再编辑或删除，只能继续追加；已迁移条目若被证明误判仍在依据，须从 Git 历史恢复回当前文件，不得反向编辑 `_history.md`。
4. 更新目标目录 `README.md`：在“日期文件”之后新增指向 `<TYPE>_history.md` 的索引行，并在写入规则中补充一句——不再被任何当前规范引用、已被后续决定完全取代的条目原文迁移到 `<TYPE>_history.md` 永久追加保存，当前文件只保留仍在直接约束行为的条目；本机制仅适用于 Harness 自身，不随下游派生。
5. 运行 `python3 -B scripts/validate_harness.py`，确认文件行数、Markdown 链接完整性与既有回归全部通过；确认 `docs/verification/`、`docs/work_plan/`、`docs/project_status/`、`docs/product_spec/` 未被触碰。
6. 若 `<TYPE>_history.md` 自身超过人工维护文本 2000 行硬上限，按本仓库既有的人工维护文本拆分惯例新建 `<TYPE>_history_2.md` 等续卷，在原文件末尾和 README 索引中注明续卷路径；不得为规避行数上限而重写或精简历史原文。

## 质量规则

- 只迁移，不改写：迁入 `_history.md` 的文本必须与原文件逐字节一致，不得摘要、润色、翻译或补充解读；连同条目自身的“恢复或调整标准”“风险”等字段一并原样迁移，不得拆散保留。
- 宁可不迁移：一条目是否仍被间接依赖难以机械判定时，保留在当前文件的代价低于误迁移到历史文件；本 Skill 不追求一次性穷尽清理，允许多轮渐进。
- 不产生新的项目记忆：本次整理属于内部维护，不因此新增或修改 Product Spec、Work Plan、Product Status 或 Verification；是否需要独立记录一条 ADR/Changelog 按各自既有触发规则判断，不因运行本 Skill 而自动触发。
- 完成后必须在回复中列出：迁移的条目标识与迁移依据（对应的完整取代声明出处）、迁移后当前文件与历史文件的行数、未迁移但存疑需要人工复核的候选条目清单。
