# 辅助重构

对既有代码做行为保持的结构性清理，只在真实出现职责不清、重复或风险信号时动手，不为假想未来预先抽象。

## 工作流程

1. 直接实施纯重构；若过程中发现真正的业务缺陷、安全问题或需要对外契约变化，停止范围蔓延，转 `$go-implement-change` 并先解决必要的授权或产品边界。
2. 行数检查限定在本次目标范围，并按文件类型应用阈值：Go 401 至 800 行、其他人工维护文本 501 至 2000 行属于建议重构/语义复核候选，逐项判断业务是否高内聚、是否围绕单一职责、各部分职责是否相近，任一项不满足时按 `docs/ENGINEERING_RULES.md` 第 2 节拆分；Go 801 行、其他文本 2001 行起必须强制拆分。不得只做格式压缩规避检查，也不自动运行全仓文件行数门禁。
3. 文件组织结构检查：
   - Go 侧一旦一个包需要拆分为多个文件，就在该包目录内按职责拆分（例如同一包下 `order.go` 只放实体与不变量、`order_query.go` 只放查询），不按类型数量、文件对称性堆积出 `models.go`、`handlers.go`、`utils.go` 这类按类型聚合的大文件；包内文件按紧密协作的类型/函数聚合，保持目录内高内聚，不得为对称性拆出没有独立职责的空文件，也不得同时保留 `xxx.go` 与同名目录造成职责歧义。
   - 只有独立发布、独立生命周期、独立权限或由工具链强制要求的依赖边界才能新增子包；新增包时必须记录它为什么不能只是现有包的一部分。
   - 两侧都遵守 `docs/ENGINEERING_RULES.md` 第 2.2 节：不使用 `utils`/`common`/`helpers`/`misc` 等兜底目录或文件名，不因文件数量或假想未来预建多层目录。
4. 命名检查修复：定位 `manager`/`processor`/`handler` 等未对应真实领域角色的泛化命名，以及无法表达职责的缩写或占位名；改为反映真实领域概念或能力的名称，改名后同步更新所有引用点与相关测试标识符。`internal/api` 下的 `handler` 是 HTTP 适配器角色的规范命名，属于允许的领域角色。
5. 常量提取：定位重复出现或语义不直观的魔法数字/字符串，提取为同一作用域内命名清晰的常量（Go `const` 块或具名类型常量）；只在确有重复或含义不直观时提取，不对单次使用的简单字面量强行抽象。
6. 潜在性能与并发问题：
   - 检查是否在持有 `sync.Mutex`/`sync.RWMutex` 期间执行阻塞 I/O 或调用可能回调回锁的函数、是否存在不一致的多锁获取顺序（应按稳定全局顺序加锁以避免死锁）、是否有 goroutine 泄漏（缺少 `ctx.Done()` 退出分支或 channel 无人接收）、是否在热路径上使用 `defer` 或反复分配可复用的缓冲区、是否用 `time.Sleep` 轮询代替条件等待（应符合 `docs/GO_WEB_TEMPLATE.md` 的并发与生命周期边界）。凡涉及并发写路径的改动必须能在 `go test -race` 下通过。
   - 检查数据访问是否越界：handler 或 service 直接持有 `*gorm.DB`、拼装原生 SQL，或绕过 repository 事务边界；这类问题按第 7 步的 core-first 归属处理，不在本步顺手改写。
   - 只修正有真实证据的问题，不做无收益的预防性优化。
7. 中文声明注释与 Core-first 复核：只对本次改动的受管声明（`struct`、`interface`、具名别名、函数、方法、测试函数）复核紧邻中文业务注释，并按 `docs/ENGINEERING_RULES.md` 第 2.1 节复核是否有接口/宿主无关的业务规则、校验、默认值或用例编排被留在适配器；发现后提升为 core 用例 API 并同步映射。日常重构不自动追加全仓中文注释门禁或依赖图门禁。
8. 重构必须保持可观察行为不变：修改后运行受影响的相关非空测试，测试名称、目录位置随迁移同步调整，不因文件移动导致测试发现失效或历史断言被弱化。Go 测试与被测单元同包时，文件移动后必须保证 `go test ./...` 仍能发现该测试。
9. 只按 `docs/ENGINEERING_RULES.md` 的独立事件触发规则更新项目记忆；纯重构、命名、常量提取、目录调整本身不触发 Product Spec、ADR、Product Status 或 Changelog，结果只在最终回复和测试/CI 中报告。发现的、当前范围外的问题登记 `docs/TECH_DEBT.md`，不顺手扩大任务。

## 硬边界

- 不得在重构中改变可观察行为、公开命令/路由/协议或业务结果；发现必须改变行为才能修复的问题时停止并转对应流程。
- 不得把 core 中已经存在的业务规则、校验或用例编排下沉回适配器；只允许把误留在适配器中的此类逻辑上移到 core。
- 不得为消除单文件超限而拆出没有独立职责边界的空壳文件或转发层；拆分必须遵循 `docs/ENGINEERING_RULES.md` 第 2 节的职责判断。
- 达到对应建议重构区间并不自动要求拆分；只有高内聚、职责单一且职责相近三项均成立时才可保留。Go 超过 800 行、其他人工维护文本超过 2000 行则无条件拆分，不接受局部理由或 ADR 降级。
- 不得引入新的目录分层约定、服务容器或子包组织规范来源；Go 包内按职责拆分文件是本 Skill 固定的默认约定，偏离需在计划或复核记录中说明局部理由。
- 不得为了性能预感改动代码而不提供可观察证据（基准、真实调用路径分析、`pprof` 剖析或已知瓶颈说明）。

## 完成输出

报告本次覆盖的文件/模块范围、行数拆分结果、目录结构调整、命名变更清单、提取的常量、识别并修复的性能/并发风险、core-first 复核结论与迁移的用例、运行过的测试与检查（含是否在 `-race` 下通过）、未处理项及记入 `docs/TECH_DEBT.md` 的条目。
