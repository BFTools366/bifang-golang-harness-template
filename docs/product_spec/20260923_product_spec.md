## 一句话目标

为 Go 服务端项目提供一套引入即用的 Harness 工程环境，让使用者在项目创建的第一天就拥有明确的方法论、文档职责划分、验证脚本、Agent Skills 与发布流程，从而可以直接按需求开发业务，而不必先自建工程规范。

## 唯一核心用户

- 使用 AI 编码代理（Codex 等）开发 Go 服务端项目的个人开发者或小团队。
- 需要一个已经封装好工程逻辑、可以直接在其上写业务的起点。

## 真实使用场景

1. 复制本模板到新的空目录，作为 Go 项目的起点。
2. 运行初始化流程，确认项目身份、接口组合与 Agent 策略。
3. 按需求开发业务模块，遵循既有的分层、注释、测试与文档规则。
4. 在本模板提供的发布生命周期下完成版本管理与发布。

## 输入与输出

| 项目 | 内容 |
|---|---|
| 输入 | 用户的产品意图、项目标识、语言与接口组合选择 |
| 输出 | 一个包含 Harness 文档体系、验证脚本、Skills 与 Go 中性脚手架的项目根目录 |

## 当前痛点

- Go 项目常见起点是「一个空 `main.go` + 一堆未成文的约定」，工程规范靠人记忆，容易漂移。
- AI 代理缺少稳定的事实来源与路由，容易重复发明结构、忽略既有边界。
- 版本管理、发布流程与验证证据通常到项目中期才补，返工成本高。

## 为什么现有方式不足

- 通用 Go 脚手架（如 `go mod init` 或 web 框架生成器）只产出代码结构，不产出工程治理。
- 源 Harness 模板绑定 Rust/Tauri 桌面技术栈，Go 后端项目无法直接复用其规则与校验器。

## 范围内（MVP）

- 语言无关的 Harness 方法论文档体系（`docs/harness_engineering/` 三分卷）。
- 文档职责划分与事实来源规则（`docs/ENGINEERING_RULES.md` §4）。
- Go 技术基线与分层约定（`docs/GO_WEB_TEMPLATE.md`）。
- HTTP API 接口边界与 Swagger 文档契约（`docs/GO_WEB_TEMPLATE.md` §4.1、§13）。
- 发布与版本管理流程（`docs/RELEASE.md`）。
- 验证脚本体系与单一入口（`scripts/`）。
- Agent Skills 体系与启动路由（`.agents/skills/`、`AGENTS.md`）。
- 中性 Go 脚手架：可编译、可运行、契约可验证，但不含产品业务。

## 范围外（非目标）

- 具体业务功能与领域模型。
- 鉴权、限流、可观测性的开箱实现（下游按需补充）。
- 一切客户端形态：不存在 GUI、CLI、TUI 或 MCP 适配器。
- 数据库迁移工具的内置集成。
- 配置中心、服务发现、消息队列等分布式基础设施。
- CI 配置文件（下游按需增加）。

## 假设

- 用户已安装 Git；Go 工具链可由环境门禁自动恢复。
- 用户接受「文档即事实来源」这一前提，愿意维护 `docs/` 下的记忆文件。
- 下游项目是本模板渲染出的 Go HTTP 后端服务。

## 约束

- 无构建步骤以外的前置工具链（不要求 Node.js、不要求 Rust）。
- 接口形态固定为 HTTP API，交付物只有服务端进程。
- 所有随附文本必须符合 `docs/ENGINEERING_RULES.md` 的行数与注释门禁。
- 模板自身不含产品事实，也不得接收产品专属请求。

## 成功标准

1. 复制模板后，`go build ./...` 与 `go vet ./...` 通过。
2. `python3 -B scripts/validate_harness.py` 通过。
3. `python3 -B -m unittest discover -s scripts` 通过。
4. 中性脚手架通过 `/healthz` 与 `/swagger/index.html` 可达性检查，且统一响应体 5 形状与稳定错误码在真实 HTTP 请求下正确。
5. 使用者按 `AGENTS.md` 的路由能在不预先加载全部文档的情况下定位到正确事实来源。
6. 初始化流程能产出一个通过上述全部门禁的唯一终端下游根目录。
