# 工程规则

本文档是所有下游项目在文件组织、代码注释、文档维护、测试组织、规则例外和机械检查方面的唯一详细事实来源。`AGENTS.md`、项目 Skills 和技术基线只保留任务入口、语言特定补充与本文件链接，不复制整套规则。

## 1. 适用范围与规则等级

- 本规则适用于所有由 Harness 建立或维护的下游项目。通用规则不绑定语言；语言或工具链文档可以增加不削弱本规则的具体要求。
- Harness 自身的文档、Skills 和随附的中性资产必须体现本规则。新建和本次修改的内容立即遵守；未触及的存量维护脚本采用渐进治理。
- 当前规范根同时包含 Harness 专用 `Version.md` 和活动 `.agents/skills/go-instantiate-project/SKILL.md` 时，该根只接受 Harness 自身工程维护，以及创建终端下游所需的固定初始化字段和所选初始化路径精确要求的身份选择。产品目的、业务功能、产品专属 UI/文案/数据、远程地址、凭据、产品构建或发布需求不得在 Harness 源中接收、分析、记录或实施；即使与合法初始化字段同一消息提供，也只能拒绝并要求用户在初始化完成、切换到唯一终端下游根目录后重新提出。
- **硬规则**用于保护架构边界、正确性、跨平台能力和交付可信度。违反时必须修复；确需例外时按第 6 节记录决策。
- **默认规则**用于保持可读性和一致性。有真实、局部且可说明的理由时可以偏离，不要求为普通组织选择增加正式决策记录。

## 2. 文件、模块与依赖边界

### 2.1 硬规则

- Core-first 是硬规则。凡不依赖某一具体接口或宿主才能成立的领域类型、业务规则、语义校验、业务默认值、应用用例与工作流编排、领域状态转换、稳定领域错误、平台无关权限、权威业务状态、迁移和持久化策略，都必须在共享 core 中实现并通过 core 自有类型的明确 API 暴露；即使当前只选择一个适配器也同样适用。
- HTTP handler 必须保持薄层，只负责运行时与依赖装配、请求语法解析、调用 core，以及把 core 结果和错误映射为接口输出。薄层按职责判断，不按文件行数、分支数或协议映射代码量判断。
- 适配器不得复制、改写或另建业务规则、平台无关校验、业务权限、权威业务状态、迁移、持久化策略或稳定领域错误。适配器处理器若需要用条件、重试或状态决策编排多个 core 调用，必须把该编排提升为一个 core 用例 API。
- 输入检查必须区分接口语法/协议结构与领域语义。无法解析、缺少协议必填字段或违反宿主能力约束的调用可由适配器拒绝；值域、跨字段关系、资源状态、业务权限、幂等性、可否执行和会改变业务结果的默认值必须由 core 判定，并在所有适配器中保留同一稳定领域错误。
- 接口或宿主特有机制属于对应适配器：例如 HTTP 路由注册、绑定/参数解析、响应序列化、状态码映射与中间件链。任何事件触发的业务行为仍必须调用 core。这些机制本身不构成 core-first 例外。
- 数据库驱动、HTTP 客户端、外部进程和操作系统 API 等具体实现集中在职责明确的适配器或基础设施模块。何时调用、允许什么、失败如何解释以及结果怎样改变领域状态属于 core；真实边界需要时可由 core 定义运行时中立的能力接口并由适配器装配实现，不得为假想未来预建抽象。
- 依赖方向必须清晰：adapter → service → repository → model 单向，下层不得反向依赖上层。`internal/router`、`internal/api`、`cmd/*` 属于适配器侧；`internal/service`、`internal/repository`、`internal/model`、`internal/apperr` 属于 core 侧。适配器彼此不得直接依赖、启动或解析对方输出。
- 数据访问必须通过仓储边界。handler 和 service 不得直接持有 `*gorm.DB` 或拼装原生 SQL；写操作必须经过 repository，事务边界由 service 定义并由 repository 实现。
- HTTP 响应必须统一使用 `internal/response` 的信封（见 `docs/GO_WEB_TEMPLATE.md`），业务错误必须使用 `internal/apperr` 的稳定错误码；错误码同时是 i18n 键，不得在 handler 内硬编码用户可见文案。
- 所有对外路由必须注册在 `internal/router` 的单一注册入口中，并经过统一中间件链；不得在 handler 内自行挂载路由或绕过中间件。
- 配置必须来自 `configs/` 的多环境文件加环境变量覆盖，通过 `internal/config` 单一入口读取。不得在业务代码中散读 `os.Getenv`，不得把密钥写进配置文件或日志。
- ID 生成统一使用 `internal/pkg/idgen` 的雪花实现；不得在业务代码中自行拼接时间戳或使用自增 ID 作为对外标识。
- 每个适配器必须直接依赖共享核心；core 不得直接或通过任何中间包反向到达 HTTP 框架、传输层或终端 I/O。适配器不得彼此依赖。
- `internal/model` 是 core 侧唯一允许依赖 ORM（`gorm.io/gorm` 及 `gorm.io/plugin/soft_delete`）的分层：表结构标签与持久化字段类型属于模型的数据契约。`service`、`apperr` 等其余 core 分层不得导入 ORM，业务规则与 ORM 必须解耦。
- 程序入口和接口处理器只负责建立运行环境、装配依赖、委托调用和映射终止结果，不得承载业务规则。
- 只有独立发布、独立生命周期、独立权限或由工具链强制要求的依赖边界才能新增 module 或子包。新增时记录它为什么不能只是现有包的一部分。
- 直接依赖和受管工具的清单必须用完整三段表达可验证的兼容下界。新增或主动更新时先选择官方 registry 当前最新非预发布候选，再以项目最低 Go 版本、peer、平台和实际 API 解析及非空测试决定下界；只有这些真实项目检查通过后才可称为“经过验证”。清单不得写 `latest`、branch、通配符或无下界范围；已安装工具处于支持范围内时直接复用。
- 受管开发环境恢复不得通过修改项目兼容要求迁就旧宿主：工具缺失时安装，可证明低于最低下界时按当前宿主路线自动升级，范围内稳定版原样复用；Go 使用连续下界 `>=1.26.0`。存在显式上界时，高于上界仍阻断；预发布、无法解析或损坏状态同样失败关闭。Go 安装到平台标准的当前用户全局位置，只持久维护标准 PATH，不创建 Harness 私有工具环境变量或私有全局前缀。只读检查必须保持零写入并明确报告 `upgrade-required`。不得降低门禁、回退依赖或 `go.sum`、注入 shim、改用旧版工具，或寻找替代工具链来适配旧环境。
- 锁文件与兼容要求职责分离：`go.sum` 固定当前真实解析结果，不是最低兼容事实。每个新增或提高的直接下界都必须在声明的最低 Go 工具链完成最低直接版本解析和非空测试；最新候选不兼容时按版本从新到旧选择第一个通过者并记录原因。
- 应用发布版本、协议/模式版本、Go 语言版本、平台目标三元组、资产摘要和按安全要求钉住的 CI action commit 不属于依赖兼容范围，不得为了形式统一改写成依赖版本范围。
- 自动生成代码、内嵌的第三方代码和人工维护代码必须明确隔离。不得直接修改生成物或内嵌的第三方内容。

### 2.2 默认规则

- 按职责、变化原因和领域概念拆分，不按类型数量、文件对称性或假想未来机械拆分。
- 一个文件围绕一个主要职责组织。总是一起变化且紧密协作的类型和函数优先放在一起。
- 出现独立领域概念、不同变化原因、平台边界或已经难以清楚维护时，应拆分文件或模块。
- Go 代码超过 400 个物理行时进入建议重构区间；其他人工维护文本超过 500 个物理行时进入语义复核区间。日常开发只报告硬超限，不因进入建议区间追加审查或阻断完成；明确发布且当次 `reviewSelection: enabled` 时，才集中检查业务是否高内聚、是否围绕单一职责，以及各部分职责是否相近，任一项不成立时按真实职责重构拆分。
- Go 包按职责建立高内聚目录，同一包内文件按职责拆分而非按类型堆积（不要出现 `models.go`、`handlers.go`、`utils.go` 这类按类型聚合的大文件）。不得同时保留 `xxx.go` 与同名目录造成职责歧义，也不得为规避行数创建空壳转发层。
- 不为每个类型或函数单独创建文件，不预建没有真实消费者的多层目录或扩展点。
- 禁止以 `utils`、`common`、`helpers`、`misc` 等兜底名称隐藏职责；共享代码必须使用真实领域或能力名称。
- 避免不能表达边界的 `manager`、`processor`、`handler` 等泛化名称。只有名称确实对应领域角色时才使用。`internal/api` 下的 `handler` 是 HTTP 适配器角色的规范命名，属于允许的领域角色。
- 单元测试靠近被测单元（同包 `_test.go`）；跨模块、接口契约与端到端测试放入 `tests/`。
- 只有转发作用且没有独立约束价值的模块应删除或合并。

### 2.3 分层代码行数门禁与通用文本上限

- Go 代码：400 行及以内不因行数触发专项复核；401 至 800 行是发布审查可见的建议重构候选，但不阻断日常任务；800 行通过，801 行失败并强制拆分。Go 包内多文件拆分必须按职责进行，不能用同名目录加空壳转发或压缩可读性规避门禁。
- 其他人工维护文本：500 行及以内不因行数触发专项复核；501 至 2000 行是发布审查可见的语义候选，但不阻断日常任务；2000 行通过，2001 行失败并强制拆分。文档、非 Go 脚本、配置、Skill、参考、模板和人工维护夹具适用此通用配置。
- 机械分类以文件后缀为准：`.go` 使用 Go 配置；其余 UTF-8 人工维护文本使用通用配置。
- 行数按与 Python `splitlines()` 等价的物理行计数，不扣除空行、注释或声明；不得通过压缩可读性、合并无关语句或移除必要注释规避门禁。
- 建议重构或语义复核区间不改变日常任务结论。只有当次发布选择启用审查时才基于真实业务边界集中判断；内容不再高内聚、未围绕单一职责或各部分职责不相近时，返回开发循环按职责拆分并修正引用后再发布。
- Go 超过 800 行或其他人工维护文本超过 2000 行时必须拆分；计划说明、审查结论、警告或 ADR 都不能把硬超限改判为通过。
- 工具生成且禁止手工编辑的锁文件/生成物（例如 `go.sum`、`*_gen.go`、`mock_*.go`），以及原样内嵌且明确隔离的第三方文件，不属于人工维护文件。这是封闭的范围定义，不是任意路径豁免；生成器、模板、补丁和维护说明仍按自身文件类型受分层规模治理。
- 文件规模治理与职责判断同时成立：文件未达到对应建议阈值不证明职责合理，adapter 未超限也不证明其符合 core-first；语义边界仍按本节其余规则审查。

## 3. 中文代码注释

### 3.1 必需覆盖

- 所有人工维护的数据结构、接口、函数和方法都必须有符合业务语义的中文注释，不只覆盖导出 API。
- 数据结构注释说明业务角色、关键状态和必须维持的不变量；语义、单位或约束不直观的字段单独说明。
- 接口注释说明职责边界、调用约定、输入输出、错误和副作用。
- 函数与方法注释至少说明其业务目的、主要处理逻辑或关键思路、重要前置条件与边界情况，以及返回结果、错误和副作用。
- 简单取值方法、构造器和薄转发函数也需要中文注释，但可以只用一句准确说明，不得为了满足格式编造复杂逻辑。
- 测试函数注释说明测试场景、关键条件、执行思路和预期结果。

### 3.2 内容质量

- 注释解释业务含义、设计原因、关键不变量和约束，不逐行翻译代码。
- 能通过更清晰的命名或结构表达的内容，先改进代码，再保留仍然必要的业务说明。
- 修改代码时同步更新相关注释。与实现冲突的注释按缺陷处理。
- 复杂算法说明不变量、阶段和取舍，不记录可直接从控制流读出的步骤。
- 非直观兼容处理、外部限制或规避方案必须说明来源、适用条件和删除条件，并链接对应决策、上游问题或官方资料。
- 使用 `unsafe`、cgo 或反射绕过类型安全时，必须紧邻安全性说明，明确调用者保证、关键不变量及其成立原因。
- 禁止保留被注释掉的旧代码；历史交给版本控制。
- 不使用署名、时间线式修改记录或“由 AI 生成”等元信息注释。
- 中文术语在项目内保持一致；代码标识符继续使用英文。

### 3.3 临时标记与有限豁免

- `TODO`、`FIXME`、`HACK` 不得裸写，必须包含具体原因和完成或删除条件。当前任务不能解决时同步登记 `docs/TECH_DEBT.md`。
- 匿名函数和极短内联回调可以由所属函数的注释统一说明。
- 自动生成代码和内嵌的第三方代码豁免；代码生成产物由生成器定义处统一说明。
- 纯声明型测试数据、静态常量集合和测试夹具可以通过所属模块或数据集说明统一覆盖。
- 豁免只消除逐项注释要求，不允许隐藏安全约束、数据来源或容易误用的业务语义。

### 3.4 机械存在性门禁

- Go 下游必须保留 `.agents/skills/go-implement-change/scripts/check_go_chinese_comments.py`，但只在本次变化需要、用户明确请求治理检查或发布/渠道硬要求时运行；日常开发和普通构建不为它增加独立步骤。它从 `go.mod` 根解析包，扫描每个包的 `.go` 文件，并对人工维护的类型声明（`struct`、`interface`、具名别名）、函数、方法、以及测试函数检查声明自身是否具有紧邻、包含至少一个汉字的注释；Go 支持 `//` 行注释与 `/* */` 块注释，两者均可作为证据，但必须紧邻声明且不被空行隔断。
- Go 门禁不要求逐字段、局部变量、匿名函数或代码生成产物；非直观字段仍按第 3.1 节语义复核。包注释、父项注释、纯英文注释或字符串中的中文不能替代声明自身的证据。以 `_test.go` 结尾的文件中，测试函数名以 `Test`、`Benchmark`、`Fuzz` 开头的声明按测试函数规则检查。
- Go 门禁只精确排除已声明的生成物（例如 `generated.go`、`*_gen.go`、`zz_generated.*.go`，以及 `vendor/`、`testdata/` 目录），不得因任意路径片段名含 `mock` 等通用词而跳过人工源码。
- Go 门禁必须对无有效扫描对象、语法残缺、非法 UTF-8、NUL、源码符号链接、坏 JSON 或运行超时失败关闭，并报告根相对文件、行、列、声明类别和名称。
- “包含至少一个汉字”只证明注释存在且归属正确，不证明内容有业务意义；语义质量仍按第 3.2 节由人工或 Agent 复核。门禁不得自动生成或批量补入“保存变量供当前逻辑使用”“执行处理逻辑”等套话。

## 4. 文档规则

### 4.1 单一事实来源

- 每项事实只能有一个权威来源。其他文档可以摘要并链接，但不得复制一份会独立演化的规则。
- 文档与代码、配置或测试冲突时，必须调查真实行为并在同一任务中修正，不能默认任一方正确。
- 文档中的命令、路径、配置项、版本和能力必须来自真实仓库，不得虚构或把计划中的能力写成已实现。
- 未确认信息明确标为“待确定”，未运行检查标为“未执行”，未实际验证的平台或行为标为 `Unverified`。
- 产品目标、边界、约束或成功标准变化时更新日期最新的 Product Spec；长期重要、难以逆转的决定和硬规则例外写入当日 ADR。范围清楚的日常实现不为每项需求创建 ADR。Product Spec、ADR、Changelog 或 Work Plan 被自身事件独立触发时，必须记录相关稳定 `change_id` 与 `$go-manage-version` 只读计算或提交结果中的 `required_version`；版本变化本身不得触发或补造项目记忆。
- Product Status 只在重要阻断、跨会话交接、真实渠道发布后的记录阶段或用户要求时更新；Work Plan 只在用户明确要求、跨会话交接或发布/高风险协调确有必要时维护；Verification 只保存真实渠道发布后追加的发布/候选验收事实，或独立回顾性人工复核/长期审计证据。
- 普通缺陷修复、不改变可观察行为的纯重构、格式整理、测试补强和内部清理本身不触发 Product Spec、ADR、Product Status、Changelog 或 Verification；结果只在最终回复和测试/CI 中报告，不写“不适用”占位。已有 TECH_DEBT 条目在问题消除后必须恢复真实状态，但不新增修复流水账。
- 构建请求、执行、成功、失败、重试、全量单元测试结果、产物路径/摘要/签名状态，以及候选 E2E、完整验收、状态更新和就绪复核，都不触发 Product Spec、ADR、Changelog、Product Status、Work Plan 或 Verification。候选事实只写入忽略的 `release/` 原子集合、manifest 声明的相邻证据和最终回复，不得复制到 tracked 项目记忆；真实渠道发布成功后，才从已发布且带版本 tag 的默认主分支开始下一次开发生命周期，记录 Verification/发布/Product Status 并 finalize 版本周期。独立回顾性人工复核或长期审计不得改写或反向批准活动候选。
- 中性初始化必须解析非空中文与英文项目展示名称，且至少一个由用户直接提供；只提供一种语言时由 Agent 自动翻译另一种，并在首次写入前通过完整汇总统一确认。`LICENSE.zh-CN.md` 只写确认后的中文名称，`LICENSE.en.md` 只写确认后的英文名称；README 身份摘要必须从同一确认结果派生，不得把机器标识当作缺失译名。
- 根 `release-notes.json` 是 Harness 源与终端下游共用的双语发布更新日志事实，不是按日项目记忆，也不替代 `docs/changelog/`。它只在准备首个正式发布时创建，使用 `schemaVersion: 2`；每个功能优化或问题修复条目把非空 `zh-CN` 与 `en-US` 文案绑定为一个翻译对，任一语言缺失、空白或同语言重复都失败关闭。每次正式发布前，根据上一次正式发布版本到当前发布源码的真实差异更新当前版本，按最新在前只保留近 5 个版本，每版“功能优化”和“问题修复”各不超过 10 个双语条目。普通缺陷修复即使不触发 Changelog，仍应进入对应发布版本的“问题修复”；失败发布可替换同版本条目。更新日志字节变化始终要求重新提交；下游还必须重新构建和验收候选，Harness 源则重新执行 Git 源码发布复核，不虚构产品候选。
- 构建不得整理、生成或改写更新日志；它只读校验发布准备已经整理的近五版。源文件、构建产物内嵌副本、manifest 摘要或运行时读取任一环不一致都阻断对应候选。
- 上一条“构建”专指发布候选。本地开发试运行属于开发制品：使用 `$go-build-local`，不读取或生成 `release-notes.json`，不写 `release/`，不提交，也不解析 E2E 选择；不得把普通“继续构建”升级解释为发布授权。
- 同一维护任务若另外改变产品目标/边界/约束/成功标准、引入长期决定或硬规则例外、形成重要阻断/交接、完成真实渠道发布，或另行进入回顾性人工复核/长期审计，才按该独立事件更新对应记忆。候选验收阶段只写忽略的 `release/` 原子证据；任务被称为“修复”或“重构”不能绕过相应的安全、发布或记录要求。
- 除上述维护排除外，用户或维护者可感知且符合 Changelog 资格的真实行为/流程变化写入当日 Changelog。修改代码或规则时仍须同步受影响的权威设计文档和测试；同步事实不等于创建项目记忆。
- 修改工程规则时，同步检查 `AGENTS.md` 的入口路由、相关 Skill、本文件和适用的机械检查；任务专属细节只在其唯一事实源中校验，不得为了通过检查复制回根入口。
- 删除或替换规则时清理失效入口、链接和摘要，避免旧规则继续进入 Agent 上下文。

### 4.3 编写、拆分与归档

- `AGENTS.md` 是启动路由器，不是全部规则的镜像。它必须保留启动门禁、按任务渐进读取、始终生效边界、非空 Skills 地图、非空约束地图和最小闭环；命中任务后再完整读取精确 Skill 与事实源，不预先加载同类全部 Skills 或无关项目记忆。
- 根 `AGENTS.md` 的 UTF-8 字节数不得超过 20,000，行数不得超过 120。新增详细初始化、依赖、构建、发布或验证规则时，正文写入既有唯一事实源或对应 Skill，根入口只增加确有必要的路由或跨任务摘要。
- 标题和首段先给结论，再补充原因、边界和证据。
- 规则必须说明做什么、何时适用、如何验证和允许什么例外，避免无法判定的“适当”“尽量”或“一般来说”。
- 示例必须标明是规范示例、占位示例还是真实验证结果，不得混淆。
- 内部链接使用相对路径；外部技术结论优先链接官方来源，并记录核对日期。
- 日期统一使用 `YYYY-MM-DD`；状态使用仓库规定的固定词汇。
- 文档不保存被删除内容的注释版本；历史交给版本控制、决策记录、验证记录或变更记录。
- 所有文档同样受 500 行建议区间与 2000 行硬上限；日常只强制硬上限，501–2000 行只在当次发布 `reviewSelection: enabled` 时集中复核。该复核优先识别独立主题，职责不再单一或相近时拆为有明确职责的文档，并由原入口保留目录和链接。
- `README.md`、`AGENTS.md`、方法论和项目记忆没有长文档例外；拆分必须保持每项事实的唯一来源、稳定入口、历史失败证据与人工复核事实。
- Product Spec、Product Status 和 Work Plan 只有触发条件满足时才写入；同一天只更新各自唯一日期文件，不得为同一天创建第二份。
- 需要在新自然日写入上述记忆时，先读取前一份，将仍有效事实、未完成事项和当日变化综合重写为完整当前快照，不得只写增量。
- 产品状态日期文件始终重写为当日完整当前状态，不累积流水账。
- 工作计划日期文件只保存当日完整当前计划。结果进入状态、验证、决策和变更记录；旧日期文件随即删除，历史由 Git 版本控制承担，不另建 `docs/archive/work-plans/` 副本。
- `docs/verification/` 与 `docs/verification/human_review.md` 只由真实渠道发布后的记录生命周期，或独立回顾性审计/人工复核生命周期写入；候选构建、E2E、完整验收和就绪复核不得为了留证污染已发布源码。其中已发布版本、真实人工复核和真实验证执行证据保留历史，不得改写为通过或删除失败事实；ADR、Changelog、Work Plan、Product Status、Product Spec 五类按日记忆只保留日期最新的文件，历史由 Git 版本控制承担。ADR、Changelog 当前最新文件行数超过人工维护文本 500 行建议重构阈值，或项目负责人明确要求整理历史记忆时，Harness 自身可通过 `$go-curate-harness-memory` 把不再被任何当前规范引用、已被后续决定完全取代的过期条目原文迁移到同目录 `_history.md` 永久追加保存；该文件只追加不改写，不是 Git 的替代品而是便于人类阅读的当前有效性过滤视图。本机制只治理 Harness 自身，不随下游派生，不适用 Work Plan、Product Status、Product Spec（三类整篇重写为当日快照，不逐条累积）。
- 同一未发布日期文件内，已被后续决定完全替代且会污染当前检索的规范描述可以合并为最新有效表述；合并必须新增 ADR 记录范围、理由、风险和恢复依据，并保留仍有效的决定编号、人工复核事实与失败证据。
- 日期文件名使用紧凑日期 `YYYYMMDD`，正文日期仍使用 `YYYY-MM-DD`。同一天不得创建第二个产品规格、产品状态、工作计划、ADR 或变更记录文件。
- 涉及产品边界、长期规则、硬规则例外或完整候选复核时先读 ADR 索引与最新日期 ADR；日常开发只在受影响区域存在相关决定时读取。只有最新条目显式引用仍有效的旧日期事实时才继续追溯。

## 5. 测试组织

### 5.1 覆盖与边界

- 每个代码行为变更必须由本次开发需要的相关非空单元/回归测试覆盖核心成功路径和最高风险失败路径；纯文档、元数据、格式或不可合理单测的机械变更只做解析或差异完整性所必需的最小替代检查。
- 修复缺陷时必须增加能够复现该缺陷的回归测试；无法测试时记录原因、风险和替代验证。
- 核心业务规则优先使用单元测试；跨模块契约、接口和真实边界使用集成或黑盒测试。
- 新增或修改业务行为时，必须先由 core 测试覆盖成功路径和最高风险领域失败，再由适配器测试覆盖输入/协议/视图映射、接口错误和生命周期。仅有适配器测试不能证明业务行为符合 core-first。
- 每个新增公开操作必须能够追溯“适配器操作 → core 用例 API → core 测试”。只修改路由注册、协议映射或平台机制而不改 core 时，计划或完成输出必须说明其接口/宿主专属性；多适配器暴露同一行为时必须复用同一 core API 和稳定领域错误。
- 外部依赖（数据库、HTTP 下游、消息队列）在单元测试中必须使用接口替身或内存实现，不得依赖真实网络或外部服务。集成测试允许使用独立临时数据库，但必须可重复、可清理且不接触真实业务数据。
- 后端测试以三层为骨架，**默认不写进程级 E2E**：
  - **单元测试（主力）**：覆盖 core 的业务规则、值域、跨字段关系与状态转换。用接口替身替换仓储与外部依赖，`go test ./... -race` 可跑。
  - **集成测试**：覆盖仓储对真实数据库的行为、事务回滚与并发冲突；用独立临时数据库，可重复、可清理、不接触真实业务数据。
  - **接口测试**：用 `httptest.NewServer` + `router.NewRouter` 打真实 HTTP 栈，逐项断言统一响应体 5 形状、稳定错误码、`Content-Language` 协商与中间件头。**这层已覆盖请求编解码、路由、中间件链和错误映射**，不需要跨进程 E2E 重复证明。
- **进程级 E2E 只保留一条冒烟链路**：真实二进制启动 → `/healthz` 返回 200 → `/swagger/index.html` 可达 → 收到 `SIGTERM` 后按 `shutdown_timeout` 优雅退出且退出码为 0。它的唯一价值是证明「交付物能起来」，不承担业务正确性责任。
- 不为单个业务功能新增进程级 E2E。业务风险用单元/集成/接口测试覆盖——跨进程 E2E 维护成本高、失败定位差，且只能证明进程能启动。
- 测试验证可观察行为，不与无关实现细节耦合；内部重构不应无故导致大量测试重写。
- 仓储测试必须覆盖事务回滚路径；涉及并发的写路径至少有并发冲突或幂等性的验证。
- 测试必须使用 `go test -race` 可稳定通过；发现数据竞争按缺陷处理。

### 5.2 隔离与可维护性

- 测试默认确定、隔离且可重复，不依赖真实网络、当前时间、随机顺序、用户主目录或机器已有状态。
- 需要文件系统时使用 `t.TempDir()`；测试不得读写真实用户数据或共享持久状态。
- 被忽略、跳过或依赖特定环境的测试必须说明原因、启用条件和影响，并在验证报告中列为未执行。
- 测试名称使用英文 `snake_case` 表达场景、条件和预期结果；测试函数按第 3 节添加中文注释。Go 测试函数必须以 `Test`、`Benchmark` 或 `Fuzz` 开头，其后接场景化英文名称。
- 小型测试夹具靠近测试；大型测试夹具放入 `tests/fixtures/`，保持只读并注明来源和用途。
- 测试辅助代码只在重复且语义稳定时抽取，禁止建立不透明的通用测试框架。
- 测试文件、测试支持和人工维护夹具按其文件类型适用第 2.3 节：Go 测试使用 400/800，其他测试支持与夹具使用 500/2000；硬超限始终阻断，建议区间只在已启用的发布审查中集中判断是否应按场景或领域拆分。

### 5.3 开发、构建与完整验收

- Git 与受管工具环境由 `$go-check-development-environment` 唯一管理：新下游在完整表单确认后、首次写入前检查，已初始化下游只在真实命令因受管环境失败后恢复一次。缺失时安装官方当前最新兼容稳定版、可证明低于最低下界时受管升级、范围内稳定版原样复用；Go 安装到平台标准的当前用户全局位置，持久去重 PATH，并在当前进程与只读取持久 PATH 的新 shell 绑定路径和版本实际复探。`GOROOT`/`GOPATH`/`GOMODCACHE` 只有在 Unix 新 login shell 或 Windows User 作用域可持久恢复且与当前进程一致时才能决定安装，否则在任何下载前失败关闭。所有会进入 PATH 的单一路径根都必须在写入或下载前拒绝对应平台的 PATH 分隔符。任何工具变化（包括仅 Git）都必须由新会话精确执行验证。Git 与 Windows MSVC 只有在平台原生受信包管理器明确要求时才允许系统级/管理员边界，必须显式可见且不得静默提权，无既有权限路线即停止。不得写项目内 shim、Harness 私有工具环境变量或让生产运行使用测试覆盖；只读模式零写入。作者身份、模板和本地提交由 `$go-configure-git-commits` 唯一管理；已有有效身份保持，缺失字段只在独立目标仓库 local 作用域补齐，绝不写 global/system。
- Harness 源与已初始化终端下游由 `$go-manage-git-lifecycle` 唯一管理开发分支到主分支的生命周期。新功能或独立 Bug 修复首次写入前自动在本地创建并切换 `feature-{ascii-kebab摘要}-{上海日期}`；创建不要求远端，碰撞使用稳定递增后缀。用户明确“推送”时，`--remote`/`state.remote` 表示唯一主远端，helper 普通合并本周期登记分支、切换其动态默认主分支并推送复读，保留登记资源；用户对本次推送逐一明确授权补充目标时，只有 `publish` 可重复接收 `--also-remote <name>`。helper 必须在首个 push 前解析全部目标及各自 advertised default branch，并把同一最终 HEAD、目标顺序和确认进度写入临时 `pendingPublish`，再逐项非强制推送、复读和保存，全部确认即清除；补充远端不 fetch、不 merge、不改绑，也不参与 release、tag 或清理。跨远端推送不是原子操作，后续失败必须如实说明可能已成功的前序范围、失败目标或阶段及后续可能未尝试；同目标重试只沿用冻结 HEAD 和进度，不重新解析默认分支、fetch、merge 或计算新 HEAD。push 非零退出仅表示结果无法确认，除非远端复读已精确命中冻结 HEAD。明确“发布”时逐次询问并锁定 `gitPublication: local | remote`：本地模式 `--local-only` 只在本地默认主分支合并、创建并复读 `v{版本}-{YYYYMMDD}`，成功后按 Worktree、本地分支清理；远端模式 `--remote <name>` 才 fetch/merge、推送并复读主分支/tag，成功后按 Worktree、主远端分支、本地分支清理。不得创建或配置远端/凭据、按前缀扫描、强制删除 dirty Worktree、删除未登记资源或在模式内 tag 门禁失败后清理。流程不设置保护分支、严格线性、活动叶子、单写入者、fast-forward-only、lease、atomic push 或审查路径等分支门禁，允许普通 merge commit，也没有任何发布中转分支及其迁移兼容代码。无关改动、疑似秘密、提交/合并/tag 失败、冲突或 dirty 最终状态始终按真实数据安全失败处理；push/远端 ref 失败仅在推送或远端发布时适用。
- 正式发布先锁定 `gitPublication`，再把源码/治理变化与独立事件已触发的 Changelog 提交并锁定 `sourceHead`；只有当前 HEAD 仍精确等于该值时，才生成发布上下文，并把且只把根 `release-notes.json` 与 `.harness/release-context.json` 作为同一个发布元数据提交。生命周期必须接收精确 `--release-context-sha256 <sha256>` 并在任何 Git 副作用前核对上下文版本、日期、tag、默认分支、模式与 remote；本地调用 `--local-only`，远端调用 `--remote <name>`，不得临时改模式。远端首次执行只在本地 fetch/整合，final HEAD 写入 pending 后才允许 push/ref/tag；pending head 非空的重试不再 fetch/merge。Harness 源在 clean 默认主分支、本地 tag 和模式要求的远端 refs 都绑定最终 `sourceCommit` 且上下文复核通过后结束；产品构建、`release/` manifest、签名、公证、产品 E2E 和产品人工验收均不适用。终端下游才继续候选构建；本地模式只允许当前宿主本地候选，远程跨平台 provider 路线只接受远端模式。`sourceHead` 保持元数据提交前的审查输入，不要求等于 `sourceCommit`。
- `release` 从关联 Task Worktree 发起时，必须先在调用 Worktree 核对当前 HEAD 中 `.harness/release-context.json` 的 blob 与 working bytes 都等于传入摘要，再路由主 Worktree；不能先切换后读取尚未合入的上下文。本地整合完成后、写入固定 pending HEAD 或执行 push/tag 前，final HEAD 中同一路径 blob 仍必须等于该摘要。
- 日常开发统一直接实施，只运行本次变更需要的相关非空单元/回归测试。不得仅因多步骤、多模块、中等风险、可并行或 Agent 偏好自动增加 Work Plan、全仓测试、格式化、代码规范、静态、集成/契约、构建、冒烟、E2E、Verification 或人工复核。
- 非必要代码/架构/职责语义审查统一延迟到明确发布。每次发布在任何写入前解析一次 `reviewSelection: enabled | disabled`：当前请求已明确时复用；安全、隐私、不可逆操作、对外兼容契约或产品/渠道硬要求强制 `enabled` 并记录来源；否则询问一次。同一发布的修复重跑复用原选择，新发布重新询问。`disabled` 只关闭非必要语义审查，绝不能跳过范围/秘密、测试、clean、签名、渠道或真正必需的人类签署；这些检查不能被解释成分支门禁。
- 已初始化下游在实施前由 `$go-manage-version` 只读分类，且只在变化完成并通过本次相关测试后提交版本：每周期首个功能使用 `feature` 提升 Minor 并锁到真实发布成功；每个具有新稳定 ID 的问题修复或用户可感知优化使用 `bug-fix` 提升 Patch 且不受功能锁影响；显式 Major 仍需用户批准。新生成 Minor/Patch 为 `0..99` 并按 base-100 自动进位，自动进位到 Major 是数值例外，不替代显式 Major 授权；Major 不受 99/100 的业务上限约束，但不得超过 Go `uint64` 上限。查询、诊断、复现、重复尝试、行为保持重构、内部优化、测试、文档、格式和清理属于 `maintenance`；`check`、`plan`、`maintenance` 都不写版本文件或状态。构建只检查版本事实/状态一致性，不能提升版本、迁移历史 `*.100.*` 状态或重置周期。
- 产品范围、长期决定、合格 Changelog、重要阻断/交接和用户明确要求仍分别触发对应记录或专用流程；候选验收只写 `release/`，真实渠道发布成功后及独立回顾性审计才在下一次自动开发生命周期写 tracked 记录。真实渠道发布成功后，下一次开发再自动创建新的 feature 分支。安全/隐私、数据迁移、破坏性操作、凭据/生产/付费副作用、对外兼容契约、渠道硬要求与发布仍保留解决当前风险必需的授权和检查；这些检查不得被实现成分支拓扑门禁。
- 显式发布候选构建在任何测试或编译前解析当前候选的 E2E 选择：当前请求已明确 `enabled`/`disabled` 时直接复用，否则询问一次；持久 `e2e_hint` 仅是建议默认值。该选择只对当前发布候选有效；本地开发试运行不解析该选择。
- 构建必须运行项目全部非空单元测试。Go 使用 `go test ./... -race` 覆盖全部包；测试失败、零测试或数据竞争阻断构建。
- 构建产出必须可复现地记录：二进制路径、`GOOS`/`GOARCH`、构建时间、源码提交和 SHA-256 摘要。交叉编译的每个平台目标必须显式声明，不得依赖宿主默认值。
- 候选构建记录严格遵守第 4.1 节的边界：manifest 和最终回复是发布候选构建的记录出口；本地开发试运行只报告实际产物路径和风险。两者都不为构建过程或结果创建、更新任何项目记忆。
- 发布候选 E2E 不混入单元测试、编译或打包命令。选择启用或产品/渠道硬要求时，只在完整最终候选存在后运行；选择禁用时记录 `Not run` 和剩余风险。
- 完整候选必须绑定批准场景、源码提交、运行环境和可观察结果；模拟实现、测试替身、占位页面、中性脚手架、开发预览或源码片段不具备验收资格。验收失败保存证据并返回开发循环；只有存在用户要求的持久计划时才重开 Todo。
- 构建候选可以标记 `milestoneAcceptance: pending`，但不是 `ready` 或发布物。若验收后的签名或打包改变产物字节、依赖或运行行为，结果是新候选，必须重新验收。

## 6. 规则例外

- 硬规则例外必须记录到当日 `docs/adr/YYYYMMDD_ADR.md`，包含被偏离的规则、理由、风险、适用范围、替代验证和恢复条件。
- Go 超过 800 行、其他人工维护文本超过 2000 行的硬上限不接受 ADR 例外；各自建议重构或语义复核区间能否保留由第 2.2 节的高内聚、职责单一和职责相近性复核决定，不属于规则例外。被机械识别为工具生成或原样内嵌第三方的文件按第 2.3 节范围定义处理，不得把普通维护文件伪装成生成物。
- 默认规则允许在计划或复核记录中说明局部理由，不要求正式决策记录。
- 例外必须尽可能小，不得从单个文件或模块自动扩张为整个项目。
- 临时例外必须有删除条件；没有明确恢复路径的例外按长期架构决定处理。
- 人工批准只授权采用例外，不会把失败或未执行的验证改判为通过。

## 7. 机械检查边界

- 可确定检查的规则可以自动化，但自动化存在不代表日常开发或普通构建必须逐项运行。显式构建固定执行全量非空单元测试和实际构建；格式、vet、lint、静态、文档链接或治理扫描只在本次变化需要、用户明确要求或发布/渠道硬要求时运行。
- Go core/adapter 的确定依赖事实应自动检查：适配器必须直接依赖 core，core 不得反向到达适配器或 HTTP 框架。检查必须覆盖包导入闭包，且不得把不含接口依赖的合法基础设施包误判为适配器。
- `TODO`、`FIXME`、`HACK` 与建议行数候选只在当次发布 `reviewSelection: enabled` 时由 `python3 -B scripts/validate_harness.py --release-review` 报告；日常 `python3 -B scripts/validate_harness.py` 只保留硬门禁。统一检查器仍必须分别对超过 800、2000 行的文件返回失败、具体路径、配置和实际行数。
- 导出 API 文档缺失可以由 `go vet` 或语言工具链判定失败。
- 中文声明注释的存在性和归属可以按第 3.4 节机械检查；注释是否有业务意义、模块职责是否合理、函数思路是否充分，必须由人工或 Agent 语义审查，不使用字符数、注释比例或关键词数量伪装成质量检查。
- 业务逻辑是否真正位于 core 同样必须由人工或 Agent 沿真实执行路径语义审查；不得用 adapter 行数、`if` 数量、文件名或关键词扫描伪装成完整证明。
- 自动检查失败必须返回非零状态并给出具体位置，不得只打印警告后宣称通过。
- 新规则只有在能够稳定判断、重复违规且人工容易遗漏时才升级为自动门禁。
- Harness 校验器只检查模板和随附的资产；真实下游代码仍由其工具链和交付流程验证。
