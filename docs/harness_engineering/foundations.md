# 基础定义、核心信念与七层模型

## 2. 什么是 Harness 工程

Harness 工程不是把提示词写得更长，而是设计模型周围的完整工程环境，使执行者能够：

- 看见正确的项目上下文。
- 理解真实目标和明确边界。
- 使用合适的工具和权限。
- 按可预期的流程推进工作。
- 从构建、测试和真实运行中获得反馈。
- 判断任务是否真正完成。
- 将决定和结果留给未来的维护者与下一次会话。

在本模板中，Harness 由七层组成：

```text
意图 → 边界 → 环境 → 执行 → 验证 → 记忆 → 生命周期
```

对应七个基本问题：

1. 为什么做？
2. 到哪里停止？
3. 如何让执行者正确理解项目？
4. 完成目标的最短可靠路径是什么？
5. 如何证明它真的可用？
6. 下一次如何无损接手？
7. 软件如何升级、维护并与用户保持联系？

## 3. 核心信念

### 3.1 一个工具只解决一个明确问题

立项必须从真实问题出发，而不是从想使用某项技术、框架或 AI 能力出发。

工具的目标应该能用一句话表达，并同时包含：

- 谁在什么场景下使用。
- 提供什么输入。
- 获得什么结果。

如果一句话需要用多个“并且”才能说完，应优先拆分问题，而不是立即扩大项目。

### 3.2 先完成最短闭环

MVP 的价值是证明核心任务能从输入走到输出，而不是提前拥有完整产品形态。

最短闭环至少包含：

```text
真实输入 → 核心处理 → 可用输出 → 明确结果反馈
```

工程流程本身也遵循最短闭环：日常任务无论步骤或模块数量都直接实施并只做本次必要测试；只有用户明确要求、跨会话交接或发布/高风险协调确有必要时才建立持久计划，只有显式发布候选构建、完整验收、发布或渠道硬要求才产生对应候选和证据。普通本地开发试运行不是候选，只报告实际产物和风险。流程证据必须与失败代价相称。

### 3.3 复用成熟能力，不重复制造非核心系统

如果操作系统、成熟软件、可靠库或标准工具已经能完成某个非核心环节，应优先通过清晰边界调用它，而不是重新实现。

复用不等于盲目增加依赖。每项外部依赖都必须回答：

- 它替代了哪部分复杂度？
- 它的安装、版本和失败方式是否可接受？
- 项目是否能够清楚检测并说明依赖缺失？

### 3.4 不为假想未来建设抽象

设置系统、插件架构、通用任务框架、复杂状态管理和跨平台抽象，不能仅凭“以后可能需要”进入当前版本。

抽象应来自已经出现的重复，而不是对未来重复的猜测。

### 3.5 极简不等于不可靠

以下通常属于 MVP 的核心可靠性：

- 不静默破坏已有用户数据。
- 不把失败报告为成功。
- 长时间操作不导致程序假死。
- 失败后能够安全重试或清楚停止。
- 输出结果可以验证。
- 发布物能够对应到明确源码版本。

以下通常属于功能扩张：

- 批量、历史记录和高级筛选。
- 主题、账户、云同步和多设备。
- 插件系统和通用配置中心。
- 自动更新、遥测和在线后台。
- 仅为潜在需求设计的多层抽象。

### 3.6 仓库是项目事实来源

会影响后续决策的产品边界、长期决定、硬规则例外和技术债必须保存在版本化仓库中。活动候选的构建与完整验收证据只保存在忽略的 `release/` 原子集合和最终回复；真实渠道发布成功后的发布证据，或被独立触发且不得反向批准活动候选的回顾性人工复核/长期审计，才通过各自受管 feature 生命周期进入版本化仓库。低风险任务的普通执行细节可以在最终回复或 CI 中概括，不需要复制进所有项目记忆。

### 3.7 用户认知是交付的一部分

用户应该能够清楚知道：

- 软件解决什么问题。
- 当前使用哪个版本。
- 本次升级发生了什么。
- 软件是否仍在维护。
- 遇到问题可以在哪里反馈。

## 4. 七层 Harness 模型

### 4.1 意图

意图层定义软件存在的理由。

每个项目创建时必须明确：

- 唯一核心用户或用户群。
- 真实使用场景。
- 输入与输出。
- 当前痛点及其影响。
- 为什么现有方式不足。
- 一句话目标。

目标描述结果，不描述实现。例如“把内部工单数据整理成可查询的 HTTP API”，优于“使用 Gin 和 GORM 开发一个后端”。

### 4.2 边界

边界层定义本次做什么、不做什么，以及软件成立所依赖的前提。

每个 MVP 必须同时写出：

- 范围内：完成闭环所必需的能力。
- 范围外：本版本明确排除的能力。
- 假设：用户环境和输入必须满足的条件。
- 约束：平台、路径、权限、依赖和交付限制。
- 成功标准：可以客观验收的完成条件。

非目标不是永久禁止。它只表示当前版本不承担这部分复杂度。未来只有在真实需求出现并重新评估后，才能进入新的版本规格。

### 4.3 环境

环境层让人和编码代理能够正确观察、理解和操作项目。

一个合格的项目环境通常包括：

- 简短项目入口和运行方式。
- 当前产品规格及非目标。
- 清晰的源码地图和模块边界。
- 确定的构建、测试和发布命令。
- 必要的工具、依赖和权限说明。
- 可重复或至少可说明的开发环境。
- 与项目规模匹配的代理指引。

应采用渐进披露：先提供一张地图，再让执行者按任务读取更深文档。不要用一个庞大的说明文件塞入所有历史知识。

当项目只有少量文件时，不必为了形式创建复杂目录。随着项目变大，可以逐步增加短小的 `AGENTS.md`、架构地图、产品原则、活跃计划和技术债记录。

### 4.4 执行

执行层定义如何以最短可靠路径完成工作。

默认原则：

- 优先简单、成熟、可直接理解的技术。
- 保持数据流短，模块职责单一，接口数量少。
- 在系统边界处校验输入和结果。
- 将平台相关行为集中到明确模块。
- 不把普通的单任务工具设计成通用平台。
- 不在没有真实消费者时增加扩展点。
- 对核心流程使用直接、可观察的实现。

执行期间若发现规格不足，应先更新意图或边界，再继续实现。不能通过临时代码决定产品行为，然后让文档被动追赶。

日常开发从清楚的请求直接实施，只增加本次必要的单元/回归测试和真正被事件触发的记录。多步骤、多模块、中等风险或可并行本身不增加 Work Plan、全仓检查、构建或验收；安全、数据、外部副作用和发布仍执行解决当前风险所必需的授权。

### 4.5 验证

验证层负责提供完成证据。构建成功不等于软件可用，测试通过也不等于用户目标已经达成。

验证按触发事件采用：

1. **静态验证**：类型检查、格式检查、代码规范检查、配置校验。
2. **自动测试**：覆盖核心状态流、边界计算和高风险失败点。
3. **构建验证**：生成真实交付格式，并检查版本、元数据和文件位置。
4. **完整真实验收**：用户要求、发布或当前发布候选启用 E2E 时，在目标环境中使用完整真实产物和真实输入完成批准场景。

日常代码行为变化只运行本次必要的相关非空单元/回归测试；非代码变更只做解析或差异完整性所需的最小替代检查。显式发布候选构建必须先逐次解析 E2E 选择并全量运行非空单元测试；本地开发试运行同样运行全量非空单元测试，但不解析发布 E2E 选择。模拟实现、测试替身、占位页面、中性脚手架、开发预览和源码片段可以服务开发，但不能作为完整验收对象；验收发现偏差时返回开发并增加回归测试。

冒烟和 E2E 只针对最终真实候选。E2E 由当前发布候选的明确选择或产品/渠道硬要求决定，持久偏好只作为询问时的建议默认值；产品定义、计划、日常编码、单元测试、编译和打包不得混跑。

测试数量不是目标。优先覆盖：

- 核心成功路径。
- 会造成数据损失的失败路径。
- 用户最容易误判结果的状态。
- 外部依赖缺失或失败。
- 版本升级可能破坏的既有行为。

任何完成声明都应说明实际执行了哪些验证，以及哪些验证因缺少环境或输入尚未执行。

### 4.6 记忆

记忆层保证项目能够跨人员、机器和会话延续。

满足对应触发条件时进入仓库的项目记忆包括：

- 产品目标/边界/成功标准变化后的当前规格和非目标。
- 长期重要、难以逆转的技术决定及理由。
- 已知限制和技术债。
- 用户明确要求持久计划或跨会话交接任务的活跃计划及当前进度。
- 真实渠道发布后追加的发布/候选验收方法和结果，或独立回顾性人工复核/长期审计证据。
- 版本历史和发布说明。
- 发布物与源码提交的对应关系。

Product Spec、ADR、Changelog、Work Plan、Product Status 五类按日文件只在仓库中保留日期最新的一份；被后续日期完全取代的旧日期文件随即删除，历史通过 Git 版本控制找回，不在仓库内另存归档副本。真实渠道发布后追加的 Verification，以及独立回顾性人工复核/长期审计证据不适用该规则，按自身规则保留全部历史；活动候选的构建、E2E、完整验收和就绪证据只存在于忽略的 `release/` 原子集合，不进入 tracked 记忆。

普通缺陷修复、不改变可观察行为的纯重构、格式整理、测试补强和内部清理的完成事实由最终回复、测试与 CI 承载，不进入 Product Spec、ADR、Product Status、Changelog 或 Verification。只有用户明确要求、跨会话交接或发布/高风险协调确有必要时才触发 Work Plan；若同时发生产品边界、长期决定、安全或审计事件，只记录该独立事件。真实渠道发布成功后再启动受管记录生命周期，候选结论不得提前写入 tracked 记忆。

文档必须有明确角色：

- 规格说明应该做什么。
- 源码说明实际做了什么。
- 测试说明哪些行为被机械验证。
- 变更记录说明各版本改变了什么。
- 计划说明尚未完成什么。

如果文档与源码冲突，应调查事实并修复其中一个，不能默认忽略差异。

文件规模治理按代码类型分层：Go 与其他人工维护文本分别从 801、2001 个物理行起始终强制拆分；401–800、501–2000 的建议区间只在当次发布启用语义审查时集中列出，届时复核业务高内聚、职责单一和职责相近性，任一项不满足就按真实职责拆分。日常开发与初始化不为软阈值增加通用审查步骤。Go 包按职责建立高内聚目录，同一包内文件按职责拆分而非按类型堆积。工具生成且禁止手工编辑的锁文件/生成物（如 `go.sum`）和原样隔离的第三方文件按封闭分类排除，不能用压缩可读性或制造“生成物”标签规避拆分。

### 4.7 版本、维护与用户关系

生命周期层从软件创建第一天开始，而不是等到“以后正式发布”再补充。

它负责：

- 语义化版本管理。
- 功能升级和缺陷修复策略。
- 发布说明和构建产物管理。
- 维护状态说明。
- 用户反馈和项目联系入口。
- 已发布版本的长期可追溯性。
