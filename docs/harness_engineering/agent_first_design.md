# Agent-first 设计、案例与完成定义

## 15. Agent-first 服务设计

当项目的主要使用者是 Codex、Claude Code 等 AI Agent，而 HTTP API 或 GUI 主要用于人类查看和管理时，产品边界、接口优先级和验收方式应当围绕机器调用设计。

Agent-first 不等于取消 GUI，也不等于把现有 GUI 操作机械地包装成自动点击。它要求先建立稳定、结构化、可验证的共享核心，再按真实消费者接入接口；本 Harness 的 Go 服务形态固定使用 HTTP API。本节其余段落保留的是语言无关的方法论背景，其中提到的 CLI/TUI/MCP/GUI 属于历史论述，不作为本模板支持的接口形态。

### 15.1 先确定主要消费者

立项时除核心用户外，还必须明确主要消费者：

- 人类直接操作：管理界面可以作为主要界面。
- 脚本和自动化：稳定 HTTP API 是主要契约。
- AI Agent：HTTP API 适合最广泛的进程调用；按目标 Agent 选择，不强制同时存在其他接口。
- 远程系统或多用户服务：HTTP API 是主要契约，需要鉴权、限流和可观测性。

主要消费者决定实现和验收顺序。若 Agent 是第一用户，不应先完成全部界面，再尝试从界面行为反推机器接口。

### 15.2 推荐分层

适合 Agent-first 项目的最小结构是共享核心加 HTTP API 适配器：

```text
共享核心 ── HTTP API：远程调用与集成
```

各层职责如下：

- **共享核心**：接口/宿主无关的领域类型、业务规则、语义校验、用例编排、状态转换、稳定错误、平台无关权限，以及权威数据的 schema、迁移和并发策略。
- **HTTP API**：把核心能力映射为路由、请求 DTO、统一响应体、错误码与中间件链。

每个适配器必须直接调用共享核心；不要让任何接口通过启动或解析另一个接口间接访问业务。适配器只校验接口语法、协议结构或宿主能力约束，值域、跨字段关系、资源状态、业务权限和会改变业务结果的默认值由核心判断。即使当前只有一个适配器，接口无关业务也必须先进入 core；这不要求为未来接口预建接口类型、容器或额外包。

中间件等机制保留在适配器；它们触发的业务动作仍调用核心。数据库驱动、HTTP 客户端、外部进程或操作系统 API 的具体实现可以位于适配器/基础设施模块，但何时调用、业务约束和结果如何改变领域状态仍由核心决定。只有真实边界出现时才抽取运行时中立的核心能力接口。

### 15.3 接口形态

本模板的 Go 服务接口固定为 HTTP API：

| 接口 | 主要消费者 | 默认定位 | 何时采用 |
|---|---|---|---|
| HTTP API | 远程客户端、前端、Agent | 唯一接口 | 需要远程调用、多用户、鉴权或集成时 |

CLI、TUI、MCP 与 GUI 均不属于本模板支持的接口形态；历史设计中的相关论述仅作背景保留。

### 15.4 已移除接口的历史说明

CLI、TUI 与 MCP 曾作为可选适配器出现在早期设计中，现已从本模板彻底移除：对应的 Skill 目录不再存在，下游初始化校验器把它们视为禁用能力。下面第 15.5 节以下保留的是当初的接口设计依据，仅作历史背景，不再构成任何实现要求。

### 15.5 MCP 契约（历史）

> 本节为历史设计依据，MCP 接口已从本模板移除，不再作为可实现的契约。

stdio MCP 由 Agent 宿主管理进程生命周期：需要时启动，连接结束后退出，不监听本地端口。

MCP 工具设计曾要求遵守：

- 一个工具完成一个清晰动作，名称使用稳定的动词和名词。
- 输入参数具有严格模式定义、必填项、枚举、长度和格式约束。
- 返回结构化数据，不把面向人的整段说明作为唯一结果。
- 工具说明明确前置条件、副作用、是否幂等和可能失败方式。
- 读取、写入、执行、破坏性操作采用不同审批级别。
- 工具数量保持克制；优先覆盖核心闭环，不镜像全部内部函数。
- MCP 与其他已选适配器通过共享核心共享相同业务规则、错误模型和权限边界；不得通过解析另一适配器的输出复用能力。

对“程序启动器”一类能够执行本机程序的工具，默认只允许启动已登记资源。新增可执行路径、修改路径、删除资源和携带危险参数应作为写入或高风险操作，由宿主请求用户审批。

### 15.6 单一数据事实来源

> 可执行的最小规则已同步到 `docs/GO_WEB_TEMPLATE.md`；本节是背景与完整设计依据。

项目内的所有接口必须读取同一份数据，不能维护互相同步的独立副本。

使用数据库作为权威存储时需要同时具备：

- 显式 schema 版本与迁移策略，不兼容变更给出清晰提示。
- 写入前校验。
- 跨进程并发控制（连接池、事务或等效机制）。
- 损坏数据的清晰报错与可恢复备份。
- 对未知字段和新增列的兼容策略。

若使用单文件配置而非数据库，还应具备：临时文件写入后原子替换、损坏文件的备份恢复、以及显式 `schemaVersion`。所有界面只能通过存储或仓储边界访问数据。若未来数据量、查询能力或并发需求超过当前存储能力，应在这一边界后迁移，而不是新增第二份事实来源。

### 15.7 人类管理界面

GUI 即使是次要界面，也应让用户能够确认系统状态和纠正 Agent 产生的变更。

通用管理型界面建议包含：

- 标题区域显示软件名、版本号和维护联系方式。
- 关于页面显示产品身份、当前版本、维护状态、核心能力、隐私或免责说明及反馈入口。
- 设置页面从少量真实设置开始，并保留清晰分组，不提前建设通用配置平台。
- 数据较多时使用数据表格：复选框、视图序号、名称、创建时间、修改时间、最后执行时间、备注和操作列。
- 数据表格支持全选、简单搜索、列头排序、分页和明确的空状态。
- 批量操作只作用于当前明确选择，跨页全选必须清楚说明范围。
- 视图中的创建、修改和最后执行时间来自核心数据，不由界面自己维护。

首版没有真实常驻需求时，不要因“以后可能需要”提前实现常驻进程或后台服务。

### 15.8 安全与可审计性

> 可执行的最小规则已同步到 `docs/GO_WEB_TEMPLATE.md`；本节是背景与完整设计依据。

Agent 能调用不代表 Agent 应自动获得所有权限。至少检查：

- 是否仅允许操作已登记或明确授权的资源。
- 进程参数是否以参数数组传递，避免拼接成 Shell 命令。
- 写入和破坏性操作是否需要审批或显式确认。
- 返回结果是否包含资源 ID、动作、时间、成功状态和真实错误。
- 是否记录最后执行时间以及必要时的调用来源。
- 日志和 JSON 输出是否避免泄露令牌、密码和不必要的本机隐私路径。
- 并行调用是否可能竞争同一数据行或重复执行同一动作。

若某项操作无法安全重试，应在 API 文档中明确标注。

### 15.9 Agent-first 实现与验收顺序

新项目默认按以下顺序建立闭环：

1. 明确 Agent 要完成的唯一任务和允许的副作用。
2. 先在共享核心实现并测试完整业务用例、稳定领域错误和单一数据事实来源。
3. 接口固定为 HTTP API，不需要接口选择。
4. 为每个所选接口建立独立、可测试的薄适配器，只映射输入/协议/视图并调用既有核心用例，不让适配器相互依赖或解析输出。
5. 日常开发直接实施，只增加本次必要单元/回归测试和真正被事件触发的记录；只有用户明确要求或跨会话协调确需时才维护 Todo。
6. 普通构建只执行明确的开发命令，不生成候选；用户明确请求正式发布候选时，先由发布准备封存范围并把当次 `gitPublication: local | remote` 与其他发布选择锁定到 tracked 上下文，生命周期携带其精确 SHA-256 且不能临时改变模式，再由构建流程在任何测试或编译前只另外解析本次 E2E 选择，并全量运行非空单元测试后生成真实候选。本地发布只形成当前宿主候选，远程跨平台 provider 只适用于远端发布。
7. 当前构建启用 E2E、产品/渠道硬要求或用户明确要求完整验收时，才对最终真实候选运行对应场景；失败时返回开发并补回归测试。

所有 Agent-first 项目必须证明共享核心与 HTTP API 接口的闭环：

- HTTP API：真实进程能启动，路由可访问，统一响应体与错误码契约可稳定解析。
- 高风险操作会触发审批或被策略拒绝。
- 并发读写不会损坏统一数据。

### 15.10 新项目决策清单

- [ ] 已明确人类、脚本和 Agent 谁是主要消费者。
- [ ] 业务能力位于共享核心，而不是 HTTP handler 或界面事件处理器。
- [ ] 当前即使只有一个适配器，接口无关业务、领域校验和用例编排也位于 core。
- [ ] 已明确接口固定为 HTTP API，不需要接口选择。
- [ ] 每个适配器直接依赖共享核心，彼此不依赖、不启动也不解析输出。
- [ ] 中间件与进程生命周期留在 HTTP 适配器，其触发的业务动作调用 core。
- [ ] 所有界面共用一个数据事实来源。
- [ ] 数据库或配置具有模式版本、迁移、原子写入和并发控制。
- [ ] 稳定 ID 与界面视图序号已经分离。
- [ ] 执行、写入和破坏性操作具有不同审批策略。
- [ ] 界面显示版本、维护入口和可核对的真实状态。

## 16. 案例：单文件转换工具

这是一个早期单文件工具（只把一个 EPUB 转成 AZW3、复用本机 Calibre、界面层只调用两个原生能力）留下的历史案例，用来具体说明单一目标、复用成熟能力、明确边界、短数据流这几条原则（见[基础分卷第 3 章](foundations.md#3-核心信念)）在真实项目里长什么样，以及极简规格仍需覆盖长任务不阻塞界面、失败时是否保留旧文件、成功状态与后续动作一致等可靠性细节。

这个案例本身预设的是单进程 GUI 直接调用本机命令行工具，早于第 15 章确立的 Agent-first 共享核心 + 适配器架构；本 Harness 当前的分层、接口选择和验收方式请以第 15 章为准，本节只作为背景例证保留，不再作为新项目应当效仿的结构范本。

## 17. 完成定义

一个项目可以宣布当前候选完整验收完成，当且仅当：

1. 唯一核心用户能够完成目标。
2. 输出在真实环境中可验证。
3. 已知高风险失败不会被误报为成功。
4. 自动检查和真实验收均绑定候选最终字节记录在忽略的 `release/` 原子集合与最终回复中。
5. 版本事实、适用的 Changelog、发布日志和候选发布物一致；正式候选必须先有本地版本 tag，且 tag、默认主分支与 manifest `sourceCommit` 精确一致。`gitPublication: remote` 时远端主分支与同名 tag 也必须一致；`local` 时不得访问远端且候选只限当前宿主。源码归档只在获得独立授权并实际生成时核对，其缺席不代替或放宽模式内 Git tag 门禁。
6. 用户能够知道如何使用、当前维护状态以及在哪里反馈。
7. 仓库足以让下一位维护者或下一次 Codex 会话恢复上下文。
8. 当前版本没有混入规格明确排除的功能。

真实渠道发布完成是候选验收之后的独立事件。只有渠道确认成功，才从带本地版本 tag、且仅在远端模式下已完成远端引用门禁的 clean 默认主分支启动下一次开发生命周期，把 Verification、发布记录与 Product Status 写入版本化仓库并 finalize；tag、上传或发布尝试本身都不能代替渠道成功。

完成不是“再也不修改”，而是当前版本的目标和承诺已经闭环。后续功能升级必须重新经过意图、边界、验证和版本判断。
