# 工作计划索引

本目录只在用户明确要求持久计划、任务需要跨会话交接或发布/高风险工作确需协调时，保存当前 Todo、状态和检查点。日常开发不自动创建 Work Plan。

缺陷修复、纯重构、多步骤、多模块、中等风险或可并行本身都不要求 Work Plan；只有用户明确要求、跨会话交接或发布/高风险协调确有必要时才创建。计划及其完成结果不自动触发其他项目记忆。

## 写入规则

- 文件名固定为 `YYYYMMDD_work_plan.md`，日期使用计划更新所在时区的自然日。
- 同一天只维护一份工作计划；计划变化后持续整理并更新当日文件，不得为同一天新建第二份。
- 新自然日首次写入时，必须读取前一份工作计划，将仍有效步骤、未完成事项和当日新范围综合重写为一份完整的当前计划；不得只追加增量。
- 日期文件是当日完整有效快照，只保留当前计划。完成结果仅在独立满足 Product Status、Verification、ADR 或 Changelog 触发条件时进入对应记忆，不因计划存在而自动联动；只保留日期最新的工作计划文件，被后续日期完全取代的旧日期文件随即删除，历史由 Git 版本控制承担。
- 已初始化下游中，每个会产生功能、具有独立稳定 ID 的问题修复/用户可感知优化（机器分类 `bug-fix`）或用户批准显式 Major 的 Todo 必须记录稳定 `change_id` 与 `$go-manage-version plan` 返回的 `required_version`；行为保持维护 Todo 明确版本不变。版本变化本身不触发 Work Plan。
- 持久计划至少包含精简 Todo：稳定 ID、预期行为、影响边界、本次必要单元/回归测试或最小替代检查，以及 `pending`、`in_progress`、`blocked`、`done` 之一。
- 发布/完整验收如已存在用户明确要求的持久计划，只能在候选期前记录待办步骤、批准场景、预期运行的全量单元测试和当前 E2E 选择；候选构建、收集、E2E、验收状态或就绪结论不得回写 Work Plan，任何 Todo 状态都不得把候选标记为 `pending`/`rejected`/`accepted` 或 `ready`。候选事实只进入忽略的 `release/` 原子集合和最终回复。
- 源码片段、模拟实现、桩、占位、中性脚手架或开发预览不能作为可验收产物；没有 Work Plan 本身不阻断用户显式请求的构建或完整验收。
