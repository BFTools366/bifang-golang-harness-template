# ADR 索引

本目录是产品边界变化、长期重要决定和硬规则例外的唯一正文来源。

## 写入规则

- 文件名固定为 `YYYYMMDD_ADR.md`，日期使用决定确认所在时区的自然日。
- 只有长期重要、难以逆转的决定、产品边界变化和硬规则例外写成独立 `ADR-YYYYMMDD-NNN` 条目；普通需求、缺陷修复、纯重构、格式整理、测试补强、内部清理和实现细节不创建 ADR。若维护任务独立引入上述决定，只记录该决定。同一天不得新建第二个 ADR 文件，而是在当日文件顶部追加并更新本索引。
- 条目至少包含状态、关联需求、背景、决定、影响范围、理由、风险、验证或替代验证，以及恢复或调整标准。
- 写入 ADR 时同步检查受影响的 Product Spec、设计/接口文档，以及已触发的 Product Status 或 Work Plan；未触发的记忆不写“不适用”占位。
- 已初始化下游的 ADR 条目必须记录相关稳定 `change_id` 与 `$go-manage-version` 返回的 `required_version`；版本变化本身不构成 ADR 触发原因。
- 同一未发布日期内，被后续决定完全替代且会污染当前检索的旧规范可以合并成最新有效描述；必须在当日新增独立 ADR 条目说明合并范围、风险和恢复依据。
- 新下游项目在产品规格仍为 `Draft` 且尚无确认需求时可以只有索引；规格转为 `Approved` 前必须创建首个当日 ADR。
- 只保留日期最新的 ADR 文件；被后续日期完全取代的旧日期文件随即删除，不在仓库中另存历史副本，历史由 Git 版本控制承担。`docs/verification/` 记录的真实人工复核和真实验证执行证据不适用本条，按其自身规则保留历史。
- 当前最新文件行数超过人工维护文本 500 行建议重构阈值，或项目负责人明确要求整理历史记忆时，Harness 自身可通过 `$go-curate-harness-memory` 把不再被任何当前规范引用、已被后续决定完全取代的过期条目原文迁移到本目录 `ADR_history.md` 永久追加保存；当前最新文件只保留仍在直接约束行为的条目。本机制仅 Harness 自身可用，不随下游派生，下游初始化不复制该 Skill 或 `ADR_history.md`。
